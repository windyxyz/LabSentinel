## 为什么会被误报

LabSentinel 的合法工作形态与恶意软件的技术画像高度重叠：

| 特征 | 恶意软件常见用途 | LabSentinel 的实际用途 |
|---|---|---|
| 无控制台 EXE 拉起脚本解释器 | 下载器 / 木马驻留 | `LabSentinel.exe`（启动器）→ `runtime\pythonw.exe` 托管本地 Web 服务 |
| 本地端口监听 + 本机 HTTP 轮询 | C2 回连 | `127.0.0.1:<port>` 的 uvicorn 服务与 `/api/health/live` 健康检查 |
| 拉起第三方二进制（go2rtc.exe / ffmpeg.exe） | 进程注入跳板 | WebRTC 实时画面网关与视频转码（MIT 许可，来源见 NOTICE） |
| 写用户目录数据 / 计划任务 | 持久化 | LOCALAPPDATA\LabSentinel 的事件库与快照（数据不出本机） |
| 无签名 / 无版本信息的 EXE | 打包器产物 | 证书未到位前的启动器（0.2.0 已注入版本资源与应用清单） |

启发式引擎（HEUR 前缀告警）不看用途只看行为组合，以上任何几点叠加都可能命中；
**这不是检测到恶意代码，代码全部开源、可审计**（AGPL-3.0，仓库见 README）。

## 我们已经做的（仓库内减面）

1. **启动链审计**（2026-11-11）：全部随包脚本无 `-c` 动态执行、无 `exec/eval`、
   无 `runpy` 动态加载；唯一的 `urlopen` 是对 `127.0.0.1` 的健康检查
   （`scripts/health_check.py` 还做了 loopback URL 白名单加固）。
2. **C# 启动器身份化**：`LabSentinel.exe` 注入程序集属性（产品/版本/公司）与
   原生应用清单（`asInvoker`——不请求 UAC 提权，杀软对"无签名 exe 请求提权"
   高度敏感）；修复了相对路径启动缺陷（见该文件头注释）。
3. **运行时来源可信**：包内 `runtime\python.exe` 来自 python.org 官方 embed 发行
   （SHA256 锁定于 `scripts/assets.lock.json`，PSF Authenticode 签名）。
4. 历史事件：2026-11-09 曾因 `install_portable.py` 内嵌「动态代码串 + urlopen +
   Popen」被卡巴斯基判杀并删除文件，已重构为独立 `scripts/health_check.py` 模块；
   2026-11-11 又发现启动器 `runpy` 相对路径缺陷与裸 EXE 画像问题，同批修复。

## 用户需要做的（证书到位前的过渡措施）

误报无法 100% 避免（证书签名是根治手段，见下）。遇到告警时：

1. **确认来源**：只从本项目 GitHub Release（或维护者分发渠道）获取安装包；
   校验 `SHA256SUMS.txt` 中对应条目（发布页附带）。
2. **加入排除/信任区**（二选一，推荐排除整个数据目录与解包目录）：
   - 便携版：解包目录（含 `runtime\`）+ `%LOCALAPPDATA%\LabSentinel\`
   - 安装版：安装目录 + `%LOCALAPPDATA%\LabSentinel\`
   - 卡巴斯基：设置 → 威胁与排除项 → 管理排除项 → 添加上述目录；
     并在「排除项」中勾选「不扫描该目录」。
   - Windows Defender：Windows 安全中心 → 病毒和威胁防护 → 管理设置 → 排除项。
3. **提交误报**（帮助所有人）：
   - 卡巴斯基 Open False Positive 通道：opentip.kaspersky.com
   - Microsoft：microsoft.com/wdsi/filesubmission（选 Software developer）
4. **不要**使用来路不明的"破解版/绿色版"——那才是真风险。

## 维护者本机复现注意事项

开发机（卡巴斯基实时防护开启）上**不要**直接执行便携包 staging/解包目录里的
runtime（`Start-Process runtime\python.exe …` / smoke 启动）——实测会触发对
整个 staging 的静默删除（2026-11-11 两次复现；构建进程内的子进程冒烟不受影响）。
本机验证便携包行为请先加信任区，或依赖 CI（GitHub runner 无杀软）跑
`smoke_portable.py`。

**2026-11-11 二分定位结论**：把发布 zip 拆成 6 个静态子集（runtime 单独 /
完整启动链 / 纯 Python 源码 / 第三方工具 / Rust bin / bat 入口）写入 TEMP
后观察 90s——**全部存活，无一被删**。证明触发点是**执行行为**（python.exe
运行启动器 → 本地监听 + 拉起第三方二进制 + taskkill 的组合）而非文件内容
特征——因此：① 把 `Resources/dist/` 与构建 TEMP 加入信任区可以完全解决；
② 静态产物无特征命中，opentip 申诉有充分依据。

**opentip 申诉材料**：`docs/archive/opentip-申诉材料-0.2.0.md`（8 个关键文件的完整
SHA256 + 可直接粘贴的申诉理由模板；zip 内容重打包后需用
`scripts/opentip_hashes.py` 思路重新生成——按 zip 内路径取哈希）。
