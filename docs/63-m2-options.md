> 状态：M1/M1.5 已收口（检测/告警/报表/便携打包，见 [62 复审](62-project-audit-2026-10-28.md)）。

## 七个方向

### A. 真实 RTSP 摄像头联调 + 24h 稳定性

- **目标**：接真机（主线程/子码流）、跑满 24h 不崩不漏报，达成发布验收。
- **现状**：RTSP 接入链路已用 go2rtc `exec:` 回环演练通过（[54 报告](54-rtsp-loopback-report.md)：
  fps 25、断线重连 ≈2s）；采样工具 `tools/camera_soak.py` 已备（CSV 指标+Ctrl+C 落盘）；
  USB/OBS 虚拟摄像头链路已通（[64](64-usb-virtual-camera-report.md)）。真实硬件从未接入。
- **工作量**：1–2 人日（联调）+ 1 天挂机观察（不占人力）。
- **风险**：夜间红外画面分布偏移可能推高误报；部分摄像头子码流路径/编码（H.265）不受支持；
  真机网络抖动模式与回环演练不同。
- **依赖**：**用户侧提供硬件**（摄像头型号、RTSP 地址、账号）、摄像头与主机同网段。
- **优先级：P0**——是发布验收本身，且为 B/D/E 提供真实数据源。

### B. 人脸识别实测（CompreFace，默认关）

- **目标**：把已集成但默认关闭的人脸模块（CompreFace）在真实环境点亮并验证。
- **现状**：服务端已有人脸管线与 `face_consents` 同意记录表；合规开关默认关闭；未实测。
- **工作量**：3–5 人日（含部署 CompreFace、注册/同意流、遮挡/侧脸误识调参）。
- **风险**：隐私与合规责任在部署方（需书面同意流程）；活体防伪 CompreFace 免费版有限；
  实验室场景口罩/帽子遮挡率高，识别率可能不达预期。
- **依赖**：**用户侧确认合规**（谁被识别、告知方式）、一台够跑 CompreFace Docker 的机器。
- **优先级：P2**——需求方明确要"认人"再做；否则是合规负担。

### C. Android APK

- **目标**：把 android/ 下 Flutter 骨架做成可安装 APK（看板+告警推送，不做端侧推理）。
- **现状**：Flutter 骨架已建；API 基址可配；无 CI 出包、无签名。
- **工作量**：2–4 人日（API 联调+构建链）+ 签名/分发另计 1 人日。
- **风险**：维护面扩大（第三端）；告警推送依赖厂商通道或轮询；纯查看端价值取决于用户手机使用场景。
- **依赖**：**用户侧提供测试手机**；对外分发需开发者账号。
- **优先级：P2**——服务已适配移动浏览器（375px 全绿），APK 是体验升级不是功能缺口。

### D. 多路摄像头吞吐

- **目标**：在 DirectML 串行锁（`Engine._run()`）下量化 2–4 路并发帧率，定降帧/抽帧策略。
- **现状**：架构上多路已支持（串行锁保稳定）；无正式多路基准数据，不编数字。
- **工作量**：2–3 人日（基准+策略+文档）。
- **风险**：DML 设备吞吐是硬上限，调优空间可能很小；结论可能是"受限于硬件"，产出偏文档。
- **依赖**：无用户依赖（演示视频即可压测）；57 任务已预留模拟压测方案。
- **优先级：P1**——A 完成后用真机数据做才有意义；纯模拟数据说服力有限。

### E. 模型迭代（飞轮第一批真实数据）

- **目标**：真实运行产生的误报回流 → 困难负样本 → 重训/评估/回滚闭环首次实战。
- **现状**：手册与工具齐备（[90 飞轮](90-data-flywheel.md)、[标注与模型迭代手册](标注与模型迭代手册.md)、
  误报截图自动入池、`tools/check_model_ready.py` 自检、v2 评估基线 [52](52-model-eval.md)）；全部环节未吃过真实数据。
- **工作量**：2–4 人日（采集标注 1–2 天 + 训练评估 1 天 + 接入回滚 1 天），训练时长另计。
- **风险**：真实误报分布可能超出 11 类词表（需增类）；训练资源窗口（GPU 规程）约束迭代节奏。
- **依赖**：**A 先跑起来才有真实误报**；标注人力（用户或标注平台）。
- **优先级：P1**——A 之后的自然延伸，直接决定系统实用口碑。

### F. 桌面客户端壳（Tauri / WinUI WebView2）

- **目标**：给便携包套一个"像软件"的桌面壳，替代裸浏览器窗口。
- **现状**：单端口模式已就绪（8000 一个端口承载 UI+API）；LabSentinel.exe 启动器（任务 55）已消除
  黑框与"脚本感"。壳的增量收益主要是系统托盘/开机自启的原生体验。
- **工作量**：3–6 人日（Tauri 或 WebView2 壳 + 打包集成 + 升级兼容）。
- **风险**：引入新工具链（Rust/.NET），与现有零依赖构建链冲突；收益与 C 类似偏体验。
- **依赖**：无硬依赖。
- **优先级：P3**——55 完成后优先级进一步下降，除非用户明确要托盘常驻体验。

### G. 部署形态与分发

- **目标**：把便携包升级为正式分发：CI 自动构建、可选安装器、自动更新、代码签名。
- **现状**：便携包+安装/卸载链路已通（[59](59-portable-install.md)、[58 策略](58-packaging-strategy.md)）；
  CI workflow 已写好并静态验证（任务 52），**启用被模型文件入库通道阻塞**（LFS/artifact，见 52 报告）；
  自动更新与签名完全未做。
- **工作量**：CI 启用 1 人日；自动更新 2–3 人日；签名 1–2 人日（需证书，年费另计）。
- **风险**：自动更新自建渠道需托管空间；无签名包会持续触发杀软/浏览器告警。
- **依赖**：**用户侧决定**是否买代码签名证书、是否有对外分发需求。
- **优先级：P1（仅 CI 启用部分）**——把已写好的流水线跑通是低成本高确定性；自动更新/签名
  等有真实分发对象再做。

## 推荐顺序与理由

**A → (E ∥ D) → G(CI) → 视需求选 B / C / F**

1. **A 先行**：发布验收本身，且是 E 的数据源、D 的真实负载。其它方向在 A 之前做完的，
   都要被 A 暴露的问题重做一遍。
2. **A 之后 E 与 D 并行**：E 吃 A 的真实误报（实用口碑），D 用 A 的真机数据定吞吐策略
   （容量口径）。G 的 CI 启用独立于 A，随时可做。
3. **B/C/F 靠后**：都是"有明确需求再做"——B 要合规确认，C 要有手机使用场景，F 在
   启动 EXE（55）之后收益递减。
