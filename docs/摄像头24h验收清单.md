# 摄像头 24h 稳定性验收清单（任务 42/78）

> 目的：发布硬阻塞「真实 RTSP 摄像头 24h 验证」的统一执行与记录方式。
> 证据归档：soak CSV、`logs/server.log` 关键段、事件截图/视频各 1 份、断线重连记录。
> **模拟/虚拟摄像头（OBS/回环）不能替代本验收**——它们不覆盖网络抖动/夜间红外/驱动异常。

## 〇、接入前预检（任务78，一条命令）

```bash
python tools/camera_soak.py --preflight --base-url http://127.0.0.1:8000
```

先在页面添加 RTSP 摄像头（不启动分析），再跑预检。通过标准：
- 服务可达 **PASS**；每个 RTSP 源 ffprobe **PASS**（codec=h264、分辨率/fps 符合预期）；
  **H.265 → WARN**（需 go2rtc 转码，建议切子码流 H.264）；ffprobe 失败 → **FAIL**（地址/网络/账号）；
- 模型/词表存在 **PASS**；数据库 integrity **PASS**；磁盘 ≥20GB（24h 粗估）；
- 疑似默认密码（admin:admin / 12345）→ **WARN**。
退出码：FAIL=2（先解决再开始 24h）、否则 0。

## 一、前置

- [ ] 真实 RTSP 摄像头可达（同网段，先 `ffprobe -rtsp_transport tcp rtsp://<ip>/<stream>` 验证）
- [ ] 码流：主码流/子码流确认；**分析建议用子码流**（720p/15fps 足够，降低解码与 DML 负载）
- [ ] 网络：有线优先；Wi-Fi 记录信号；摄像头与服务器时钟大致同步（事件时间可信）
- [ ] 磁盘：`%LOCALAPPDATA%\LabSentinel` 所在盘剩余 ≥ `LS_DISK_MIN_FREE_GB`（默认 5GB）
- [ ] 告警渠道（可选）：配置一个测试渠道，验证告警链路
- [ ] 服务端启动正常：`/api/system` 200、backend 为 directml（或预期后端）

## 二、步骤

1. 启动服务端（便携包 `启动.bat` 或源码 `一键启动.bat`）。
2. 添加摄像头：类型 `rtsp`、源 `rtsp://<user>:<pass>@<ip>/<stream>`；先**不启动**分析。
3. 画安全区（覆盖目标区域）+ 规则（enter L2 / enter_no_ppe L3，cooldown 按现场 5–30s）。
4. 启动分析 → 确认 `status=running`、fps>0、首条事件出现、截图可看。
5. 启动采样器（另开窗口，只读不干扰；任务78 多路口径）：
   ```bat
   :: 全部摄像头一起采样（多路汇总进同一个 CSV/JSON）
   python tools\camera_soak.py --base-url http://127.0.0.1:8000 --all --duration 24h --interval 30 --stall-s 60
   :: 单路（可重复 --camera-id）
   python tools\camera_soak.py --camera-id 2 --duration 24h --out logs\soak-cam2.csv
   ```
   产物：`soak-<时间戳>.csv`（每路每采样点一行，含 fps/帧龄/重连/last_error/CPU/磁盘）+
   同名 `.json` 汇总（判定 PASS/WARN/FAIL、API p50/p95、事件增长、磁盘下降）。
   **中断恢复**：Ctrl+C 随时落盘并出摘要；中断后可换 `--out` 文件续采（分段拼接）。
6. 期间（建议 12h 左右时）做一次**主动扰动**：断摄像头电源或拔网线 30–60s → 恢复；
   记录恢复耗时（参照 docs/54 回环演练：预期秒级重连、worker 不死）。
7. 结束：停止采样器（Ctrl+C 也会落盘）→ 读取摘要 → 归档证据。

## 二.5、PASS/FAIL 判定（发布证据要求）

| 项 | PASS | WARN | FAIL |
|---|---|---|---|
| 24h 连续 | 全程服务可达、无重启 | 1 次内自动恢复 | 服务死亡/重启 ≥2 次 |
| worker | 每路 running ≥99% | 偶发重连恢复 | 路级 running <99% 或死亡 |
| 事件/截图 | 事件持续、抽查截图可看 | — | 长时间零事件（有人场景） |
| 磁盘 | 下降在预估内 | 预警未触发紧急清理 | 磁盘写满/触发紧急清理 |
| 汇总判定 | soak JSON `verdict=PASS` | `WARN`（记录原因） | `FAIL` |

## 三、通过标准（建议阈值）

| 项 | 标准 |
|---|---|
| API 可用率 | ≥ 99%（服务端自身重启应记录原因） |
| camera running 占比 | ≥ 99% |
| 非预期中断 | 无 > 60s 的非 running 持续（主动扰动除外，单独记录） |
| fps | 不低于配置分析帧率的 80%（如 LS_ANALYSIS_FPS=5 则 ≥4.0） |
| 事件 | 24h 内持续产生（数量与现场人流相关，无硬阈值） |
| 整机 | 无死机/重启/蓝屏（Windows 事件查看器无 Kernel-Power 41） |
| 资源 | 内存无持续增长趋势（对比首尾 tasklist） |

## 四、证据归档

1. soak CSV（`logs/soak-*.csv`）+ 摘要文本
2. `logs/server.log` 起止各 1 段 + 断线重连时间点前后各 20 行
3. 事件截图/视频各 1 份（证明分析质量在 24h 后仍正常）
4. 主动扰动的时间点与恢复耗时
5. （可选）首尾各一张 UI 截图

## 五、不通过时

- API 可用率低：查 server.log 是否 5xx/崩溃；区分服务端问题与网络问题
- fps 长期低于 80%：确认子码流/分辨率/LS_ANALYSIS_FPS 配置；检查 CPU/GPU 占用
- 整机死机：按《训练安全规程》同思路排查（事件查看器 + WHEA/Kernel-Power），先降负载
  （LS_ANALYSIS_FPS 调低、单路）再逐步恢复
