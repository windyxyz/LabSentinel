# 训练安全规程（2026-10-27，两次死机事故后制定）

> 依据：docs/80-risk-register.md A1、docs/51-loadtest-report.md §3（子代理根因分析）。
> 结论：软件根因（DML 并发）已修复；**本机在高负载组合下仍不稳**（CPU 满核 + GPU 推理 + 虚拟显示器/剪映；ACPI EC 超时；WUDFRd 0xC0000365）。训练因此必须受控执行。

## 允许谁训练

- ✅ 定时巡检任务（满足本规程全部前置条件）
- ✅ 主会话/用户（人工执行同样遵守）
- ❌ 任何与压测/批量推理并行的场景

## 前置条件（全部满足才允许启动训练）

1. **CPU 负载 <30%**（连续两次采样间隔 5s，powershell 取 LoadPercentage）
2. **子代理近 10 分钟无文件变更**（降低代码被改 + 并发源）
3. **无其他重任务**：任务管理器无高 CPU 的 python 进程（压测/批量推理）
4. **无训练锁**：`.training.lock` 不存在（存在说明已有训练在跑或上次异常中断）
5. 服务端如在高频推理（有摄像头 running）→ 先停摄像头再训练（WAL 里 status=running 的置 stopped，或提示主线）

## 训练命令（固定，不许改参数）

```bash
# 后台执行，日志 logs/train_v2.log；先写 .training.lock（记录 PID 与时间）
D:/LabSentinel/m0-venv/Scripts/python.exe -c "
import torch; torch.set_num_threads(6)   # 限线程！不许满核
from ultralytics import YOLO
m = YOLO('m0-spike/yolo11n.pt')
m.train(data='datasets/merged/data.yaml', epochs=24, imgsz=640, batch=8,
        workers=0, device='cpu', fraction=0.5, patience=8,
        project='runs', name='ppe_v2', exist_ok=True, seed=42)
"
```

## 训练期间的纪律

- 巡检只做**文档核对与看板更新**；**跳过 pytest / npm build / 任何验收测试**
- 不启动第二个训练，不跑压测，不批量推理
- 不做大文件复制/磁盘密集操作

## 看门狗（每次巡检检查）

1. `.training.lock` 存在 → 读 PID，检查进程是否存活（`tasklist /FI "PID eq <pid>"`）
2. 存活的进程 CPU 应接近 6 线程满载；日志 logs/train_v2.log 有进度输出
3. **进程消失**：
   - 有新产物（`runs/detect/runs/ppe_v2/weights/best.pt` 的 mtime > lock 的 started_at）→ 视为正常完成，进入下方"完成链路"
   - 否则视为异常退出（可能机器重启/被杀）→ **不自动重启训练**；看板记录"训练异常中断"，等待主线/用户决策
4. 看门狗从不在训练运行时开启其他重活

## 完成链路（训练正常结束后由巡检执行）

1. `tools/eval_report.py` 跑 test split → 逐类 AP 记入看板
2. `tools/export_onnx.py` 导出 → `m0-spike/yolo11n_ppe.onnx`
3. 从 `datasets/merged/data.yaml` 生成 `m0-spike/yolo11n_ppe.classes.txt`
4. **不重启服务端**、不改 `.env`；看板写"v2 模型就绪，待主线/用户重启接入（按 docs/45-model-onboarding.md §2–3）"
5. 删除 `.training.lock`

## 硬件侧建议（用户侧处理，软件侧无法根治）

- 更新/回退 BIOS 与芯片组驱动；更新核显驱动
- 停用不用的虚拟显示适配器（Parsec / GameViewer，见设备管理器；每次开机 WUDFRd 加载失败 0xC0000365）
- 若仍不稳定：`LS_BACKEND_ORDER=cpu` 排除 DML；或降低分析帧率/路数
