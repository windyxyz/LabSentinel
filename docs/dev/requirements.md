# 10 · 需求文档

> 状态：v0.2（2026-10-25）· 第一轮追问已收口，❓ 全部消除

## 角色

- **安全管理员**：配置摄像头、安全区、告警规则；处理告警；查报表。
- **实验室人员**：被监测方；人脸功能开启时是注册人员（需单独同意）。
- **系统**：无人值守运行的分析服务。

## 用户故事（核心集）

1. 作为安全管理员，我想添加一路 RTSP 摄像头并划定安全区，以便系统知道"哪里需要穿实验服"。
2. 作为安全管理员，我想在有人未穿实验服进入安全区时收到告警（带截图），以便及时纠正。
3. 作为安全管理员，我想看到每个实验室当前在场人数和按天/时段的进出统计，以便掌握使用情况。
4. 作为安全管理员，我想配置"告警规则"（区域×时段×行为×级别）和冷却期，以免被告警轰炸。
5. 作为安全管理员，我想回查某段时间的事件并看到当时的短视频/截图证据。
6. 作为安全管理员，我想开启人脸比对（默认关闭）后注册人员，并在**未注册人员进入**时收到告警。（已确认：用途是安全管理的陌生人发现，不做考勤）
7. 作为安全管理员，我想在实验室用的 IM（企业微信/微信/QQ/邮件）里收到告警，以便手机上第一时间看到。

## 功能需求

### FR1 视频流接入
- **支持矩阵**（已确认由技术侧定）：
  - ✅ 任何输出 **RTSP** 的 IP 摄像头（海康/大华/宇视/TP-Link/小米等，均提供 RTSP）；分析走**子码流**（640–720p），实时观看走主码流。
  - ✅ USB 摄像头、本地视频文件（开发与演示；无 IP 摄像头时可用手机装"IP 摄像头"类 App 模拟 RTSP）。
  - 后期：ONVIF 设备自动发现；远期：GB28181（国内安防标准，接入存量平台的亮点）。
- 路数：**MVP 按 1 路实现、按多路设计**（配置即列表），多路扩容是确定需求。

### FR2 安全区与规则配置
- Web 端在摄像头快照上绘制多边形安全区（支持多个）。
- 规则 = 安全区 × 时段 × 行为类型 × 严重级别 × 冷却期。

### FR3 防护合规检测
- **MVP：只检测实验服（白大褂）**，"人员 + 实验服"两个类做扎实，精度优先。
- 扩展（M2+）：护目镜、手套、口罩。
- 精度/召回可配置（宁可少报不误报，或反之）。

### FR4 人员检测、跟踪与计数
- 人员目标跟踪（跨帧身份保持）。
- 进出事件（计数线/安全区进出）、在场人数、按时段统计、长时间滞留（后期）。

### FR5 人脸比对（可选模块，默认关闭，M2 实现）
- 用途（已确认）：**识别进入者是否为注册人员 / 发现陌生人**，安全管理导向；不做考勤打卡。
- 开启前置条件：管理员显式开启 + 注册人员单独同意记录（功能内建同意登记）。
- 注册人员管理（照片→特征入库，仅本地存储）；1:N 比对；未注册人员进入事件。
- 匿名计数模式下完全不运行任何人脸相关计算。

### FR6 事件与告警（渠道为插件式架构，多平台接入）
- 事件记录：时间、摄像头、类型、截图、（可选）前后数秒短视频。
- 通知渠道排期：
  - **M1**：应用内实时（WebSocket）+ 企业微信群机器人 webhook + SMTP 邮件。
  - **M2+**：钉钉机器人；微信触达优先走"企业微信应用消息"（可推到个人微信，官方通道）；Server酱/PushPlus 备选；小程序订阅消息（随小程序端）。
  - **QQ**：个人 QQ 无官方机器人通道，提供邮件兜底；OneBot 自建方案作为社区可选适配器（协议风险用户自担）。
- 告警聚合与冷却期；按级别区分。

### FR7 管理后台（Web）
- 摄像头管理、实时画面查看、安全区绘制、规则管理、事件检索、报表（进出/违规统计）、人员库（人脸开启时）、系统状态（GPU/CPU/路数/帧率）。

### FR8 客户端多端（原则：原生/高性能渲染，拒绝 WebView 套壳）
- **原则（用户拍板）**：跨端方案必须原生渲染——Electron / Tauri / uni-app 经典版这类 WebView 套壳一律不用（"直接用网页不好吗"）。见 [adr/0003](./adr/0003-native-client-flutter.md)。
- **M1：Web**（响应式，手机/桌面浏览器）。
- **M2：Android** —— Flutter（备选 Compose Multiplatform / Kotlin 原生，M2 启动时定）。
- **M4：桌面客户端（Windows/macOS/Linux）+ iOS** —— Flutter 同一代码库；鸿蒙走 Flutter OHOS 社区移植（届时评估成熟度，不达标则放弃该端）；微信小程序与 Flutter 无法共享代码，若确有需要再做独立实现（uni-app 仅用于小程序端，不是主客户端）。

### FR9 部署形态与分析位置
- **一体机模式（默认）**：服务端部署目标 **Windows / macOS / Linux**（Docker 优先 + 原生降级路径，M0 先验 Windows）。
- **Android 小模型部署**：作为**实验性部署目标**（旧手机/盒子跑 nano 级模型，NCNN/TFLite 路线），M4+ 评估，不进核心架构承诺。
- 客户端-服务端模式：同一套服务，多端远程访问。
- **所有 AI 分析都在服务端**（已确认）：摄像头→服务端→事件/告警；客户端零 AI 依赖。"端侧模型/云端 API"为后期实验特性。见 [adr/0002](./adr/0002-server-side-analysis.md)。

## 非功能需求

| 项 | 要求 |
|---|---|
| 分析延迟 | 事件产生 ≤ 3s；实时画面延迟 ≤ 1–2s（WebRTC，M0 验证） |
| 模型规模 | **小型模型优先**（nano/small 级，用户明确要求"模型不用特别离谱"）；目标：纯 CPU 跑 1–2 路子码流，GPU 加速为增强而非前提（具体指标 M0 实测后写死） |
| 硬件 | 部署机有 GPU+CPU（具体型号未知，M0 实测回填） |
| 隐私 | 默认匿名计数；人脸数据仅本地；数据保留期配置与一键清除 |
| 合规 | 满足《人脸识别技术应用安全管理办法》设计要求（见 20-research/00-synthesis.md 第 7 节） |
| 开源 | 代码 AGPL-3.0；模型/数据集安装时下载（协议各异，不随库分发） |
